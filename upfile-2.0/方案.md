# 高性能文件上传下载平台 - 用户系统与空间赠送功能设计方案

## 1. 业务背景
当前平台为主客单一模式（使用配置文件里的 admin 认证），所有的文件上传没有严格的用户隔离以及存储上限限制。随着平台的发展，需引入多用户体系，赋予每个用户个人的存储空间额度，并引入类似于“数字资产”的概念，允许用户互助，提出**用户相互赠送上传存储空间**的功能，提高系统灵活性及用户互动率。

---

## 2. 数据库设计变更

### 2.1 新增 `users` 表 (用户信息与配额)
用于管理注册用户信息及其独立的存储配额。
*主要字段：*
- `id` : `INTEGER PRIMARY KEY AUTOINCREMENT`
- `username` : `TEXT NOT NULL UNIQUE` (用户名，用于登录及被赠送)
- `password_hash` : `TEXT NOT NULL` (密码哈希值，提升安全性)
- `total_space` : `INTEGER DEFAULT 10737418240` (总空间额度，默认 10GB，单位 Byte)
- `used_space` : `INTEGER DEFAULT 0` (已使用空间，单位 Byte)
- `created_at` : `DATETIME DEFAULT (datetime('now','localtime'))`
- `status` : `INTEGER DEFAULT 1` (用户状态: 1-正常, 0-封禁)

### 2.2 新增 `space_gift_records` 表 (赠送流水表)
用于追溯存储空间的流向，防止并发下对账不清或恶意刷空间。
*主要字段：*
- `id` : `INTEGER PRIMARY KEY AUTOINCREMENT`
- `from_user_id` : `INTEGER NOT NULL` (赠送方用户 ID)
- `to_user_id` : `INTEGER NOT NULL` (接收方用户 ID)
- `gift_size` : `INTEGER NOT NULL` (转移的容量大小，单位 Byte)
- `created_at` : `DATETIME DEFAULT (datetime('now','localtime'))`
- `remark` : `TEXT` (赠送备注或寄语)

### 2.3 改造原有的 `files` 表
文件必须产生真正的归属关系。
- *新增字段*：`user_id` `INTEGER DEFAULT 1` (关联 `users.id`，默认为 1 以兼容历史无主数据)

## 3. 分析与设计：用户注册流程

### 3.1 页面交互逻辑
1. 在现有的登录页，添加【账号注册】的切换按钮或跳转链接。
2. 注册表单提供：**用户名**、**密码**、**确认密码**。
3. 对用户输入进行前端有效性校验（不得含特殊字符或过短等）。

### 3.2 接口设计 (`POST /api/auth/register`)
- **请求参数**：`{ "username": "user1", "password": "password" }`
- **执行逻辑**：
  1. 查询 `username` 是否在 `users` 表中已存在；存在则返回提示 `用户名已被占用`。
  2. 对密码进行不可逆加密（推荐使用 `BCrypt` 算法）。
  3. 数据插入 `users` 表，初始化10G容量额度（`total_space`）。
  4. 注册成功后返回状态码，前端重定向去登录或者直接派发 JWT Token 让用户视为登录完成。

## 4. 分析与设计：用户赠送上传空间流程

### 4.1 核心业务规则
- **安全边界**：用户可赠送的容量，必须 <= 自身的**可用剩余容量** (`total_space - used_space`)，且必须正向操作（即增量不得 <= 0）。
- **事务一致性**：赠送操作涉及【扣减A的空间】+【增加B的空间】+【新增流向记录】，三者必须在同一事务里（All or Nothing），防止两边数据对不平。

### 4.2 页面交互逻辑
1. 位于用户的**个人中心**或者**控制中心**，新增一个模块显示“总空间”、“已用空间”、“可用空间”进度条及状态。
2. 旁边提供按钮【赠送给他人】。
3. 弹出表单：
   - 输入**对方用户名**。
   - 输入**赠送的存储空间大小 (MB/GB)**。
   - 要求输入**登录密码**进行二次身份确权（防止账号未退出的误操作或盗用）。
4. 确认后提交请求，页面自动刷新最新的容量进度。

### 4.3 接口设计 (`POST /api/space/gift`)
- **请求参数**：`{ "toUsername": "target_user", "giftSizeMb": 1024, "verifyPassword": "..." }`
- **执行逻辑**：
  1. 通过当前登录用户的 Token 获取其 `fromUserId`，并从数据库重查自身 `users` 记录。校验二次密码是否匹配。
  2. 根据 `toUsername` 查找目标用户 `toUserId`，若查无此人，返回 `目标用户名不存在`。若目标是自己，拒绝操作。
  3. 将提交的 MB 转换为 Byte (`giftByte = giftSizeMb * 1024 * 1024`)。
  4. *开启数据库事务 (@Transactional)*。
  5. 校验可用空间：`free_space = total_space - used_space`。若 `free_space < giftByte`，直接返回报错 `操作失败：自身可用空间不足`。
  6. 【扣减赠送方额度】：`UPDATE users SET total_space = total_space - #{giftByte} WHERE id = #{fromUserId}`。
  7. 【增加接收方额度】：`UPDATE users SET total_space = total_space + #{giftByte} WHERE id = #{toUserId}`。
  8. 【新增流向记录】：`INSERT INTO space_gift_records ...` 用于日后审计。
  9. *事务提交*，返回成功响应。

## 5. 本方案对原有系统需做的联动修正（关键！）
引入配额模块后，原上传和删除流程必须受到管制：
1. **上传阻拦 (`/api/upload/init`)**: 必须计算剩余空间是否足够容纳 `file_size`，不够则直接打回，阻止上传会话的创立。
2. **容量扣费 (`/api/upload/complete`)**: 文件分片拼合成功且落库 `files` 后，必须执行 `UPDATE users SET used_space = used_space + file_size`。
3. **容量返还 (`/api/file/delete` 及 `定时任务`)**: 当用户主动删除，或者超期文件被系统计划任务清理时，在删除 `files` 记录的同时，必须执行 `UPDATE users SET used_space = used_space - file_size`，将空间额度归还给该账号。
